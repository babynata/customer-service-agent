## 2. 需求概述

### 2.1 用户故事

**作为** 使用客服 Agent 的终端用户  
**我希望** 用口语化的方式提问也能得到准确答案  
**以便** 不需要刻意使用标准关键词就能获得帮助

**作为** 运营人员  
**我希望** 系统能告诉我哪些用户问题没有命中 FAQ  
**以便** 我能持续补充和优化知识库

**作为** 开发者  
**我希望** FAQ 检索延迟 < 200ms，准确率 > 85%  
**以便** 不影响客服 Agent 的实时交互体验

## 3. 功能需求详述

### 3.1 FR-01 语义检索

**需求描述**  
用户输入"我想退货"，系统应能匹配到"退款"相关的 FAQ，即使关键词不完全一致。

**验收标准**
- 同义词匹配准确率 ≥ 80%（测试集：50 组同义词对）
- 口语化表达匹配准确率 ≥ 70%（测试集：30 组口语化 query）
- 延迟 < 200ms（P0 方案，含 API 往返）

**输入/输出**

```
输入："东西坏了能换不"
输出：{
  matched: true,
  answer: {answer: "收到商品如有损坏，请拍照联系客服...", confidence: 0.82},
  sources: [{key: "商品损坏", score: 0.82}]
}
```

### 3.2 FR-02 混合检索

**需求描述**  
在纯向量检索基础上，增加关键词命中 bonus，弥补 embedding 模型对特定领域术语理解不足的短板。

**验收标准**
- 关键词 bonus 加分 0.08~0.15
- 最终分数不超过 1.0
- 混合检索准确率比纯向量检索提升 ≥ 5%

**规则**
- 如果 query 完全包含 FAQ 关键词：+0.15
- 如果 query 包含 FAQ 同义词：+0.08
- 如果上一轮对话意图与 FAQ 分类一致：+0.05

### 3.3 FR-03 降级兜底

**需求描述**  
当 Embedding API 超时、限流或返回错误时，系统必须自动降级为关键词匹配，保证服务可用性。

**验收标准**
- Embedding API 失败时，100% 降级成功
- 降级延迟 < 50ms
- 降级时 thinking_log 标注「Embedding 降级 → 关键词匹配」

**降级触发条件**
- API 返回 4xx/5xx
- 连接超时（> 3s）
- API Key 未配置或无效

### 3.4 FR-04 阈值控制

**需求描述**  
不同 FAQ 条目可能有不同的置信度要求（如退款政策要求高置信度，而活动规则可放宽）。

**验收标准**
- 全局默认阈值：0.72
- 支持按 category 配置不同阈值
- 支持按单个 FAQ 条目配置阈值

## 4. 非功能需求

### 4.1 性能

| 指标 | P0 目标 | P1 目标 |
|------|---------|---------|
| 检索延迟（P99） | < 200ms | < 50ms |
| 吞吐量（QPS） | 10 | 100 |
| 支持 FAQ 数量 | ≤ 1000 | ≥ 100,000 |
| 准确率（Top-1） | ≥ 75% | ≥ 90% |

### 4.2 可用性

| 指标 | 目标 |
|------|------|
| 服务可用性 | 99.9% |
| Embedding API 失败降级成功率 | 100% |
| 数据丢失 | 0（向量库有备份） |

### 4.3 安全

- API Key 不硬编码，通过环境变量注入
- query 长度限制 ≤ 500 字符
- 敏感词过滤（复用现有 final_check 节点）

## 5. 运营需求

### 5.1 数据看板（P1）

运营后台需展示：
- 每日检索量 / 命中率 / 平均置信度
- Top-20 未命中 query（按频次排序）
- Top-20 低置信度命中（0.72~0.85）
- FAQ 条目命中率排行

### 5.2 审核工作流（P1）

```
系统发现新未命中 query
  ↓
聚类归类（自动）
  ↓
运营审核 → 补充 FAQ / 补充同义词 / 忽略
  ↓
自动 Embedding + 更新向量库
```

### 5.3 A/B 测试（P1）

支持对比不同策略的效果：
- 向量检索 vs 关键词匹配（基线）
- 不同阈值（0.70 / 0.72 / 0.75）
- 不同 embedding 模型（bge-large / bge-m3）
